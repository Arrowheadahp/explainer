How Superpowers makes a coding agent build software

A plugin of 15 markdown files that turns a code-generating agent into a wait-for-approval, test-first, reviewed, hand-off-ready engineering process.

You type "let's build a React todo list" into an AI coding agent. The default failure mode is famous: it starts writing files within seconds, invents requirements you never mentioned, and hands you something that mostly works and is partly untested. obra/superpowers (by Jesse Vincent and Prime Radiant, MIT-licensed) is a plugin that changes that default. It is not a code generator, a model, or a framework. It is a set of written procedures — skills — plus a small bootstrap that makes an agent load and obey them, plus a handful of shell scripts and prompt templates that move work between agents as files rather than as chat.12

This page traces the mechanism end to end: what the agent is given at startup, what it is forced to produce before code exists, how plans are split into tasks, how sub-agents are dispatched and reviewed, what files accumulate on disk, and where the whole thing is designed to break. It describes the repository as of release v7.0.1 (commit 2ce8aa1, October 2026). That date matters: Superpowers is unusually fast-moving, and earlier versions looked quite different.

Scope of this page. Every factual claim below was checked against the repository source, the Agent Skills specification, or the host harness documentation, and is cited inline. Worked-example commit SHAs, line counts, and test counts in §4 are constructed to show the artifact formats faithfully, not lifted from a recorded session; that is stated there and in the Sources.

1 · Prerequisites

Four ideas carry everything else. None requires prior knowledge of Superpowers.

  • Agents have tools and a context window. A "coding agent" is a language model running in a loop: it reads files, edits files, runs commands, reads results, and repeats. Everything it has seen so far sits in its context window. That window is finite and, once full, gets compacted — replaced by a lossy summary. Anything the agent only "remembered" from earlier turns can vanish.4
  • Sub-agents are blank-slate agents. Most harnesses let an agent spawn another agent with its own fresh context and its own instructions, then wait for a short reply. A sub-agent does not inherit the parent's history. It only knows what the dispatch prompt told it.1
  • A skill is a markdown file with a description. Under the open Agent Skills format, a skill is a directory containing a SKILL.md with YAML frontmatter (name, description) and a markdown body. The description is shown to the agent for every installed skill; the body is loaded only when the skill is used. Supporting files — references/, scripts/, assets/ — load even later, on demand. This three-level loading is called progressive disclosure.3
  • Git plumbing. Commit, branch, and worktree: a worktree is a second checkout of the same repository in a different directory, on its own branch, sharing one object store. It is how an agent can work without disturbing your current checkout.8

Two pieces of engineering vocabulary also recur. TDD (test-driven development) means write a failing test, watch it fail, write the minimum code that passes, then refactor — Red, Green, Refactor. YAGNI ("you aren't gonna need it") means don't build what nobody asked for. Superpowers treats both as rules, not preferences.6

2 · Big picture

Superpowers installs into a coding agent through two channels. First, a bootstrap: at session start (or, depending on harness, on the first user message), the plugin injects the full body of one skill, using-superpowers, into the conversation. That text tells the agent it has skills, that it must check for a matching skill before responding, and that if a skill applies it has no choice but to invoke it. Second, the plugin registers the 15 skills so the agent can list and load them on demand.

From there the work follows a fixed pipeline. Brainstorming pulls intent out of you and ends in an approved design document. A git worktree isolates the work. A written plan breaks the design into tasks of two to five minutes, each with exact file paths, interfaces, and a Red/Green test cycle. Execution — either one fresh worker per task, or the session agent itself — lands every task through a review gate. Code review and a whole-branch review catch drift. A finishing step asks you, explicitly, whether to merge, open a pull request, or keep the branch.1

Figure 1 rewards reading the violet nodes first. There are only six points where the run actually stops for you: the brainstorm conversation, the builder check's questions, approval of the design document, the worktree consent question (only when no isolated workspace exists), the execution-mode choice, and the closing integration menu. Everything between them is the agent working uninterrupted — which is why the skill boxes vastly outnumber the question boxes, and why the skills devote so much text to the rule that a running plan does not stop to ask "should I continue?".

Then read the artifact boxes. Two are committed and outlive the run: the design document and the plan. One is the permanent record itself: the commits. Three kinds are scratch — the progress ledger, the task briefs and reports, and the review diffs — written so that context trouble cannot lose work, and deleted once the branch is finished. If you remember one thing from the figure, make it that asymmetry: the durable outputs are the ones you review before they are made, and the disposable ones are the ones the agent uses while making them.

Three design decisions explain most of the structure you are about to see. One: process before craft. Skills that set how to work (brainstorming, debugging, planning) take priority over skills that do what to build. Two: artifacts over conversation. Design docs, plans, task briefs, reports, review packages, and a progress ledger are files, because the agent's memory is not reliable across compaction. Three: fresh context as a quality tool. A reviewer that did not write the code, and a worker that never saw the parent's 60,000-token history, both catch things the author cannot.7

3 · The mechanism, step by step

3.1 Bootstrap: making the agent use skills at all

A pile of markdown is useless if the agent ignores it. The bootstrap solves that problem, and it is worth understanding because it is where the whole system's authority comes from.

On Claude Code and several other harnesses, Superpowers registers a SessionStart hook, matched to startup, clear, and compact. The hook is a small POSIX shell script, hooks/session-start. It reads skills/using-superpowers/SKILL.md, escapes it into JSON, wraps it in an <EXTREMELY_IMPORTANT> envelope, and prints it in whichever JSON shape the current harness consumes — Cursor's additional_context, Claude Code's nested hookSpecificOutput.additionalContext, or the SDK-standard top-level additionalContext.2

{
  "hooks": {
    "SessionStart": [
      { "matcher": "startup|clear|compact",
        "hooks": [ { "type": "command",
                     "command": "\"${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.cmd\" session-start",
                     "shell": "bash", "async": false } ] }
    ]
  }
}

Two details in that JSON matter more than they look. The matcher includes compact, so the bootstrap is re-injected after the context window is summarized away — the agent is reminded it has skills precisely when it is most likely to have forgotten. And run-hook.cmd is a polyglot wrapper: a single file that is valid batch script on Windows and valid shell on Unix, so one hook definition works on both.2

Other harnesses differ. Antigravity has no session-start event, so there the bootstrap arrives by a different route: the agent sees each skill's description, and using-superpowers's description ("Use when starting any conversation") prompts the model to load it in its first turn. OpenCode's plugin does not use a hook at all; it injects the bootstrap as the first user message via the harness's message-transform API, and deliberately skips that injection in child sessions so workers do not restart the design workflow their parent already authorized.2

Four lines of using-superpowers do the enforcement work:

If you think there is even a 1% chance a skill might apply to what you
are doing, you ABSOLUTELY MUST invoke the skill.

IF A SKILL APPLIES TO YOUR TASK, YOU DO NOT HAVE A CHOICE. YOU MUST USE IT.

This is not negotiable. You cannot rationalize your way out of this.

**Invoke relevant or requested skills BEFORE any response or action** —
including clarifying questions, exploring the codebase, or checking files.

The rest of that skill is a table of red flags — the exact sentences an agent tends to think right before skipping a skill — paired with the reality that defeats each one. "This is just a simple question" → "Questions are tasks. Check for skills." "I need more context first" → "Skill check comes BEFORE clarifying questions." "I remember this skill" → "Skills evolve. Read current version."5

That table is not decorative. The repo's own skill-authoring guide says these tables exist because its authors tested skills by running sub-agents through pressure scenarios — "production is down, every minute costs $5k, do you read the debugging skill first or fix it now?" — recorded the rationalizations the agents produced, and wrote counters for each. Writing skills is itself treated as TDD: a skill is not shipped until an agent has been observed failing without it.51

3.2 Brainstorming: from a sentence to an approved design

brainstorming triggers on anything creative — a feature, a component, "planning anything new, in software or out of it". Its premise is stated in its first paragraph: the agent "build[s] what you believe your human partner wants, and that belief is usually thinner than it feels."6

The skill is strict about the shape of the conversation, not just its content:

  • Look before you ask. In an existing project, read the files the user pointed at before sending the first message. Never ask what the project already answers.
  • One question per message. Each message ends with exactly one sentence-long question and no menu of example answers, because options steer; open questions surface intent. A menu is offered only when the user is stuck.
  • Play it back. As each part of the picture becomes clear, the agent restates that part in 200–300 words, marks its own guesses as guesses, and asks what is wrong or missing. Playback and questions alternate.
  • Lay out approaches, then write the doc. Before writing, it presents two or three real ways to build the thing, what each trades off, and a recommendation, and asks the user to choose. Then — not before — it writes the design.
  • Size the work. A small change gets a short design agreed in chat; a project gets a full written design. If the work grows mid-task, the agent stops and steps up a size.

The full design must be something "a talented builder in the domain could plan from without going back to your human partner": intent and why, goals, non-goals, anti-goals (what would make this a failure even if it technically works), constraints, the approaches considered, the decisions already made, and what is explicitly left to the builder. It is written to docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md and committed. The repo's own history follows its own rule — docs/superpowers/specs/ holds design documents like 2026-05-05-platform-neutral-config-refs-design.md, complete with scope, substitution rules, commit plan, verification steps, and non-goals.6

Before the design reaches you, a builder check runs: a fresh sub-agent is told it is "a talented [DOMAIN]" who has been handed this document and cannot talk to its author, and is asked to report only the questions it would still need answered to plan the work well, ranked by importance, skipping anything the document leaves to the builder. The agent sorts the answers into three piles — already answered (fix the document), minor (decide it yourself and mark it as your call), and theirs (bring to the user in one message).6

The hard gate. brainstorming ends with an explicit <HARD-GATE>: "Nothing gets built until your human partner approves the design doc… Building includes writing product code, scaffolding, installing dependencies, creating projects, and invoking an implementation skill. Reading and exploring are fine." Two exceptions exist: the user opted out of the questions, or the user approved a labelled throwaway spike — and keeping anything a spike produced is a new request that goes back through the gate. After approval, the skill instructs the agent to invoke superpowers:writing-plans "and no other skill".6

Note what this replaces. The default failure is not that the agent writes bad code; it is that it writes code for a problem it guessed at. Here, all the thinking that normally happens as silent guessing happens as a conversation with you, and is then frozen in a document you signed off on.

3.3 Worktree isolation: a clean, verifiable starting point

using-git-worktrees runs after design approval and before any implementation. It is written defensively, in three steps.8

Step 0, detect existing isolation. Compare git's Git directory with its common Git directory. If they differ, you are already in a linked worktree and creating another would be wrong. A submodule guard exists because submodules produce the same inequality: if git rev-parse --show-superproject-working-tree returns a path, it is a submodule, not a worktree. Only in a plain checkout does it ask: "Would you like me to set up an isolated worktree? It protects your current branch from changes."

Step 1, create it. Prefer a native harness tool (EnterWorktree, /worktree, a --worktree flag) over calling git worktree add yourself, because a native tool keeps the harness's own bookkeeping consistent; using git behind its back creates state it cannot see or clean up. With no native tool, it falls back to git worktree add, choosing a directory in priority order: your declared preference, then an existing .worktrees/ or worktrees/, then .worktrees/ by default. Before creating anything project-local it runs git check-ignore, and if the directory is not ignored it adds it to .gitignore and commits that first — otherwise the entire worktree could get committed into the repo.

Steps 2 and 3, setup and baseline. Auto-detect the stack (npm install, cargo build, poetry install, go mod download) and then run the test suite. If the baseline is red, the agent reports the failures and asks whether to proceed. This is the point of the exercise: "A dirty baseline makes every later failure ambiguous."

3.4 Writing plans: the plan is the argument, the spec is the authority

writing-plans converts an approved design into a document for "an engineer who has not seen this codebase or this spec". The plan opens with a fixed header: goal in one sentence, architecture in two or three, tech stack, a path to the spec (so the spec "travels with" the plan), a Global Constraints section of project-wide requirements copied verbatim, and a Review Focus section naming the handful of input classes or failure modes most likely to hurt a real user but that no task's tests exercise. Plans are saved to docs/superpowers/plans/YYYY-MM-DD-<feature>.md.7

Before defining tasks, the skill maps the files the change will create or modify and what each is responsible for, because that mapping is where the decomposition gets locked in. Tasks are then drawn to a specific size: "the smallest unit that carries its own test cycle and is worth a fresh reviewer's gate," which in practice means roughly two to five minutes of work and one independently testable deliverable. Setup, configuration, and documentation steps get folded into whichever task actually needs them.7

Each task is a block of this shape — the real template, abridged only in the test body:

### Task 3: Retry wrapper for the sync client

**Files:**
- Create: `src/sync/retry.py`
- Test:   `tests/sync/test_retry.py`

**Interfaces:**
- Consumes: `SyncClient.send(payload: dict) -> Response` (Task 2)
- Produces: `retry_send(client, payload, attempts=3) -> Response`

- [ ] **Step 1: Write the failing test**

```python
def test_retries_three_times_then_succeeds():
    ...
```

- [ ] **Step 2: Run test to verify it fails**

Run: `pytest tests/sync/test_retry.py -v`
Expected: FAIL with "cannot import name 'retry_send'"

- [ ] **Step 3: Implement `retry_send(client, payload, attempts=3) -> Response`**

- [ ] **Step 4: Run test to verify it passes**

Run: `pytest tests/sync/test_retry.py -v`
Expected: PASS

- [ ] **Step 5: Commit**

```bash
git add src/sync/retry.py tests/sync/test_retry.py
git commit -m "feat: retry failed sync sends"
```

Three things in that template carry the system's weight:

  • The Interfaces block. Each task's implementer sees only its own task. "Produces" tells later tasks the exact names and types to consume; "Consumes" tells this task what earlier tasks promised. This is what lets independent workers be dispatched in any order without talking to each other.
  • Steps are Red/Green actions with Expected: lines. "Write the failing test" / "run it and see it fail" / "implement the minimum" / "run it and see it pass" / "commit" are separate steps with checkable results, so the executor can compare reality against the plan one step at a time.
  • A deliberate ceiling on detail. "A step is done when the implementer can write exactly one reasonable thing from it. That is the whole requirement: unambiguous, not complete." A plan longer than the code it describes has written the code instead; lines that decide nothing ("TBD", "handle edge cases", "add appropriate validation") are the opposite failure. The plan's self-review checks exactly this, along with spec coverage and cross-task type consistency — clearLayers() in Task 3 and clearFullLayers() in Task 7 is the example given.7

The plan ends with a handoff that asks you to choose an execution mode: subagent-driven (a fresh worker and a fresh reviewer per task, then a whole-branch review) or native/inline (the session agent implements everything itself, with one fresh reviewer at the end). The skill's prompt template asks the agent to recommend one, in a sentence, based on how coupled the tasks are, how many there are, and what a shipped mistake would cost.

3.5 Execution mode A: subagent-driven development

Subagent-driven development (SDD) is the thorough mode. Its core principle is one line: "Fresh subagent per task + task review (spec + quality) + broad final review = high quality, fast iteration."9

Setup. Verify the worktree. Then create the plan's private workspace by running bash scripts/sdd-workspace PLAN_FILE, which prints a git-ignored directory under <repo-root>/.superpowers/sdd/<plan-basename>/ and writes a plan-path marker file naming the owning plan. Every artifact for this plan — ledger, briefs, reports, review packages — lives there and nowhere else, so a second plan in the same checkout cannot overwrite the first one's progress. The agent reads the plan once, reads the spec it names, creates one todo per task, and runs a pre-flight conflict scan: one row for every pair of tasks sharing a file or interface, one row per task checking its own internals, each conflict ruled on and written to the ledger before Task 1 is dispatched.9

The per-task loop. Four steps, repeated:

  1. Record BASE, then dispatch the implementer. git rev-parse HEAD is stored before dispatch — the review range will run from this commit, never from HEAD~1 (which silently drops all but the last commit of a multi-commit task). The task's text is extracted to its own file with bash scripts/task-brief PLAN_FILE N; the dispatch prompt references that path as the single source of requirements, plus a one-line explanation of where the task fits, any interfaces from earlier tasks the brief cannot know, the agent's resolution of any ambiguity, and the report-file path.
  2. The worker implements. It reads its brief, asks questions if anything is unclear, implements, runs TDD, commits, self-reviews, writes a full report to its report file, and returns a reply capped at 15 lines: status, commit SHAs, a one-line test summary, concerns, and the report path.
  3. Build the review package, dispatch the reviewer. bash scripts/review-package PLAN_FILE BASE HEAD writes one file containing the commit list, a diffstat, and the full diff with ten lines of context, named review-<base7>..<head7>.diff. The reviewer receives that file's path, the brief, the report, and the binding global constraints, and returns two verdicts: spec compliance (missing / extra / misunderstood) and code quality (Critical / Important / Minor).
  4. Fix loop or complete. Clean review → one line in the ledger: Task N: complete (commits a7..b7, review clean). Findings → the fix loop. Minor findings never enter it; they are recorded as Task N: minor (deferred): … for the final reviewer to triage.

Four rules in the dispatch and review steps are the ones most worth copying into your own process, because each fixes a failure the maintainers observed:

  • Never make a worker read the whole plan. It gets a brief. A real session's dispatch prompt, they note, once reached 42,000 characters, 99% of which was pasted history from earlier tasks. What a fresh worker needs is its task, the interfaces it touches, and the global constraints — nothing else.
  • Workers never dispatch sub-agents — not helpers, "and above all never spawn a reviewer to check your work." Every worker-spawned reviewer duplicated the review the controller was already going to dispatch, at full cost.
  • Never dispatch two implementation workers in parallel, because they would conflict. (Parallelism belongs to read-only work: the dispatching-parallel-agents skill is for independent investigations.)
  • Never pre-judge the reviewer. If the prompt you are writing contains "do not flag", "don't treat X as a defect", "at most Minor", or "the plan chose", stop — that is pre-judging, usually to spare yourself a review loop. And never tell a reviewer to re-run tests the worker already ran; the worker's report is the test evidence.

Model selection. A section of the skill that saves real money: match model capability to role, and always name the model explicitly, because an omitted model inherits the session's model — often the most capable and expensive one. Mechanical single-file tasks with a complete spec get the cheapest tier; integration and judgement get a standard model; final review is dispatched on the most capable model. The skill also notes that turn count, not token price, dominates cost: cheap models routinely take two to three times as many turns on multi-step work.9

"Rulings, not stalls." A running plan does not wait for a human. When a conflict, ambiguity, or plan defect appears, the controller decides, using the spec as the binding authority and the plan as its argument, and writes Ruling: <what you decided> — <why> — <what it costs if wrong> into the ledger. The skill's justification is blunt: "A wrong ruling costs rework your human partner can see and undo; a session parked on a question costs their whole day and buys nothing." Exactly four things stop an execution run: an irreversible or destructive operation; a security-sensitive action; a side effect outside the worktree that norms say to ask about first (a merge, a push to a shared branch, a publish); and a plan so broken that every path forward is a guess.9

3.6 Execution mode B: executing plans inline

SDD pays for a fresh implementer and a fresh reviewer on every task, each re-reading the codebase from zero. Inline execution pays for one context — the session's — plus a single reviewer at the end. It is the cheap mode, and the skill is candid about what it gives up: no fresh context per task and no second pair of eyes per task. It compensates by other means: "the brief is the spec, the ledger is your memory, TDD is the per-task gate, and the final reviewer is the second pair of eyes."11

Mechanically it is the same ledger, the same workspace, and the same plan format — the two skills explicitly share them, "so a plan can change executors mid-flight and the new one resumes from the same ledger." The differences are that the session agent is the implementer, and that completion is recorded by a script rather than a reviewer: scripts/task-done PLAN_FILE N BASE -- <test command> runs the tests, keeps full output in the workspace, prints the tail, and only appends the ledger line if they pass. A failing run records nothing. TDD is loaded as a required sub-skill before Task 1, and the final review is still dispatched to a fresh reviewer on the most capable model.

3.7 The innermost loop: TDD and the evidence rules

Every task, in either mode, ends in the same enforcement: test-driven- development, whose Iron Law is a single sentence — NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST — and whose consequence is unusual: "Write code before the test? Delete it. Start over… Don't keep it as 'reference.' Don't 'adapt' it while writing tests. Don't look at it. Delete means delete."6

Why so absolute? Because the skill's argument is about proof, not purity: "Tests written after pass immediately — which proves nothing. You never watched it fail, so you never proved it can catch the bug." A test that passes the moment you write it is a finding about the test. This is why plans give each test step an Expected: FAIL with "<message>" line — the executor must compare the real failure text to the predicted one, and a failure for the wrong reason is not a Red.

The companion skill, verification-before-completion, closes the same loop at the level of claims: NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE. Before saying a task is done, the agent identifies the command that would prove it, runs the full command, reads the full output, and only then makes the claim. "Should pass" is disallowed; "Agent said success" is disallowed — check the diff.12

3.8 Debugging: four phases and a three-fix ceiling

systematic-debugging is the other skill that fires constantly. Its Iron Law: NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST. Phase 1 reads the error properly, reproduces it reliably, checks recent changes, and — in multi-component systems — adds instrumentation at each boundary and runs once to see where the break is, before forming any theory. Phase 2 finds a working example and lists every difference. Phase 3 states a single hypothesis and tests it with the smallest possible change. Phase 4 writes the failing test that reproduces the bug, implements one fix, verifies, and only then claims success.13

The most interesting number in the skill is an architectural tripwire: if three fixes have failed, stop fixing and question the architecture. "This is NOT a failed hypothesis — this is a wrong architecture." Escalating at three turns an endless guessing loop into a design conversation.

3.9 Reviews, finishes, and the human decisions

Reviews are task-scoped gates, then one broad gate. The task reviewer verifies the diff against the brief (nothing missing, nothing extra, nothing misunderstood) and against quality, with the instruction "Do not trust the report… Design rationales in the report are claims too… a stated rationale never downgrades a finding's severity." When every task is done, a whole-branch review runs on the most capable model, against a package spanning git merge-base main HEAD..HEAD, pointed at the ledger's deferred-minor and parked lines so it can triage them. Findings get exactly one fix wave and one scoped re-review — never per-finding fixers, and no second wave.910

Then finishing-a-development-branch takes over, and the pattern is the same throughout: verify, then ask. It runs the full suite (on the tree about to be integrated, not "earlier this session"), detects whether it is in a worktree, confirms the base branch, and presents exactly three options — merge locally, push and open a pull request, or keep the branch as-is. Discarding work is not on the menu; it exists only if you explicitly ask, and then requires typing the word discard. Cleanup has an ownership rule: it removes worktrees under .worktrees/ or worktrees/ (the ones it created) and leaves everything else, because that belongs to your environment. And if removal is refused because untracked files exist, it never force-removes — it shows you the files and asks.14

4 · Worked example: Task 3 of a real plan

Numbers won't illustrate a process, so this example traces one task through every artifact it touches. The plan is a small one — a CLI that syncs records over an unreliable network API. Suppose Tasks 1 and 2 have already been completed and reviewed; the ledger starts like this:

# SDD ledger — plan: docs/superpowers/plans/2026-03-02-record-sync.md
Pre-flight: Task 3 produces retry_send consumed by Task 4's bulk path. No conflict.
Task 1: complete (commits 4b1c9e2..7d0a3f1, review clean)
Task 2: complete (commits 7d0a3f1..a55e0b8, review clean)

Step 1 — record BASE and cut the brief. Before dispatching, the controller records BASE = a55e0b8 (Task 2's head, which is where Task 3's change begins) and runs task-brief. The extractor's awk walks the plan, tracking fenced code blocks so a ### Task 3 heading quoted inside a code sample cannot fool it, and writes the task's text through the next task heading:

$ bash scripts/task-brief docs/superpowers/plans/2026-03-02-record-sync.md 3
wrote /repo/.superpowers/sdd/2026-03-02-record-sync/task-3-brief.md: 41 lines

Step 2 — dispatch the worker. The dispatch prompt is short by design: where this fits ("third of nine tasks; it wraps the client Task 2 built"), the brief path as the source of requirements, one interface from Task 2 the brief cannot know, the report path, and the contracts. The worker asks no questions, implements, and runs TDD:

RED   pytest tests/sync/test_retry.py -v
      FAILED  ImportError: cannot import name 'retry_send'   expected reason
GREEN pytest tests/sync/test_retry.py -v
      1 passed                                               minimal code
SUITE pytest -q
      47 passed                                              full suite clean
$ git add src/sync/retry.py tests/sync/test_retry.py
$ git commit -m "feat: retry failed sync sends"
   [sync-api d31f2a4] feat: retry failed sync sends

It writes task-3-report.md with the RED command, the failing output, why the failure was expected, the GREEN output, the files changed, and its self-review notes. Its reply to the controller is four lines:

Status: DONE
Commits: d31f2a4 feat: retry failed sync sends
Tests: 47/47 passing, output pristine
Report: /repo/.superpowers/sdd/2026-03-02-record-sync/task-3-report.md

Step 3 — package and review. The controller runs review-package PLAN a55e0b8 d31f2a4. Two guard checks inside the script matter: it exits 3 if d31f2a4 is not a descendant of a55e0b8, and exits 3 if the range is empty — both symptoms of being on the wrong branch would otherwise produce a silently bogus review package. The package is one file:

# Review package: a55e0b8..d31f2a4

## Commits
d31f2a4 feat: retry failed sync sends

## Files changed
 src/sync/retry.py       | 31 +++++++++++++++++
 tests/sync/test_retry.py| 24 +++++++++

## Diff
(two hunks with ten lines of context)

The reviewer reads that one file, reads the brief and the report, and returns:

### Spec Compliance
- ❌ NotImplemented: "Sleep between attempts with backoff `0.1 * 2**n`
  seconds", brief step 3 — no sleep in `retry_send` (src/sync/retry.py:14-28)
- ✅ Return type matches the Interfaces block (`Response`)
- ⚠️ Cannot verify from diff: Task 4's use of `retry_send` in the bulk path

### Strengths
- Failure message asserted verbatim from the brief; test fails for the
  expected reason (tests/sync/test_retry.py:8-19)

### Issues
#### Critical (Must Fix)
- Retry loop catches bare `Exception` (src/sync/retry.py:22) and would
  retry a permanent 400 the same as a 503.

#### Important (Should Fix)
- No backoff between attempts (spec: `0.1 * 2**n`)

#### Minor (Nice to Have)
- Constant `3` inline; name it (src/sync/retry.py:12)

### Assessment
**Task quality:** Needs fixes

Step 4 — fix loop, round 1 of 5. Spec ❌ triggers the loop. The worker is resumed (rounds 1–3 resume the original, whose context is intact) with the findings verbatim. It writes a test proving the backoff first, watches it fail, fixes, re-runs the covering tests, appends a fix report, and commits. A scoped re-review reads only the fix diff (d31f2a4..e07b911) and verdicts each finding ADDRESSED or NOT ADDRESSED. The ledger then records:

Task 3: fix round 1/5 (3 addressed, 0 open — bare-except, backoff, constant;
        commits d31f2a4..e07b911)
Task 3: minor (deferred): inline constant 3 — named in fix, test not added
Task 3: complete (commits a55e0b8..e07b911, review clean)

Count what the artifacts bought. The worker never saw Tasks 1, 2, or 4, so its 41-line brief and 5,000-token context stayed cheap. The controller never saw the diff, so its context — which still has six tasks to run — stayed clean. The reviewer, who wrote neither the code nor the plan, caught a spec item the implementer had quietly skipped and a bug the tests did not cover. And if the session had been compacted after Task 5, the ledger plus git log would have told a new controller exactly where to resume, which commits exist, and which decisions had already been ruled on.

5 · The artifact inventory

This is the part people usually get wrong when they describe Superpowers as "a prompt pack". The prompts are half of it. The other half is a set of typed, on-disk artifacts, each with an owner, a lifetime, and a reason to exist.

5.1 Shipped in the plugin

ArtifactWhereWhat it is, and why it exists

5.3 Produced while working — scratch, git-ignored, deleted at the end

All of these live in <repo-root>/.superpowers/sdd/<plan-basename>/. The directory writes a self-ignoring .gitignore containing *, so nothing leaks into git status without touching a tracked file, and a plan-path marker file proves which plan owns the directory.

ArtifactFilenameWriter → readersWhy it is a file

Two lifetimes are worth noting. The scratch artifacts are explicitly temporary: once the final review is clean and its fixes are merged, the skill tells the executor to delete the plan's workspace, because "the git history is the record now." The ledger is a recovery map for the run, not an archive of it. And a plan can switch executors mid-flight: both execution skills use the same ledger format in the same directory, so a new executor resumes at the first task without a Task N: complete line — the handoff between modes is a file format, not a conversion step.911

5.4 The meta-artifact: skills themselves

writing-skills treats a skill as a testable artifact. The mapping it gives is explicit: test case = pressure scenario with a sub-agent; production code = the SKILL.md; test fails = the agent violates the rule without the skill; test passes = it complies with the skill present; refactor = close the loopholes the agent finds.15

It also carries the most transferable lesson in the whole repository, and it is about form, not content. Match the guidance to the failure type: a rule violated under pressure needs a prohibition plus a rationalization table plus red flags; output with the wrong shape needs a positive recipe that says what the output is, because agents negotiate with prohibitions; a required element in something the agent already produces needs a structural slot in a template; and behaviour that depends on a condition needs a conditional keyed to an observable fact, not an unconditional rule with an exemption clause. They report that in head-to-head wording tests on dispatch prompts, the prohibition arm produced clearly more of the unwanted content than the recipe arm — and trended worse than the no-guidance control. A single "unless it matters" nuance clause, appended to a winning recipe, degraded it from consistent to noisy.5

6 · Deeper layers

6.1 The equations: context economics and loop termination

Superpowers' architecture is largely an answer to one constraint: an agent's context is finite and does not survive summarization. The skills describe the cost of a dispatch in exactly these terms — everything pasted into a prompt "stays resident in your context for the rest of the session and is re-read on every later turn." For a dispatch of \(P\) bytes re-read at every one of \(t\) turns, that is a per-turn tax proportional to the prompt, paid for the whole session:

\[ c_{\text{per turn}} \propto \frac{P}{4}\ \text{tokens} \qquad c_{\text{context}} = t \cdot c_{\text{per turn}} \]

The expressions above are this page's illustration of the relationship the skills describe; the division by four is a convention for estimating tokens from bytes, not a constant Superpowers publishes. What Superpowers states is the qualitative claim and its own observed example. The conclusion it draws is the architecture: hand artifacts over as files, not pasted text, so a task brief costs a path in the controller's context and a single read in the worker's. The 42,000-character dispatch quoted in §3.5 is the counterexample the rules were written against — roughly ten thousand tokens of mostly-pasted history, before the worker does anything.

The same thinking explains the bounded fix loop. Each round costs a fix dispatch plus a scoped re-review, and past a point rounds stop converging because the failure is structural rather than informational. The skill encodes that as a hard cap with an escape hatch rather than an unbounded while-loop:

\[ \text{round} \in \{1,\dots,R_{\max}\},\quad R_{\max}=5 \;\Rightarrow\; \begin{cases} \text{resume original implementer}, & \text{round} \le 3,\\[2pt] \text{fresh implementer, model } m+1, & \text{round} \in \{4,5\},\\[2pt] \text{adjudicate and ledger a ruling}, & \text{still open at } R_{\max}. \end{cases} \]

Model tier at round \(r\) escalates by one for \(r \ge 4\); the reasoning is that "a loop that survives three resumes usually means the implementer cannot see its own problem," so fresh eyes and a capability bump come together. The controller's own decision is recorded, never silent; a silent discard is forbidden.10

6.2 Edge cases the skills handle explicitly

  • A worker says "this is too hard." That is a success, not a failure. The implementer template states "Bad work is worse than no work. You will not be penalized for escalating," and defines a fourth status, NEEDS_CONTEXT, separate from BLOCKED. Each status routes differently: context problem → supply context and re-dispatch same model; reasoning problem → more capable model; task too large → split it; plan wrong → rule, ledger, re-dispatch with the ruling carried in the dispatch.9
  • The plan itself is wrong. The spec is the authority; the plan is its argument. The smallest change that satisfies the spec wins, ruled and ledgered. "Deviating from the plan without a ledgered ruling is a decision made in secret."
  • The reviewer cannot verify something from the diff. Reported as a ⚠️ item, not as a pass or a fail. The controller then decides whether it is a real gap. The reviewer is also told not to broaden its search: "evidence you cannot see is not evidence that doesn't exist."
  • The maintainer's own plan mandates a defect. A finding labelled plan-mandated is still a finding — "the plan's authorship does not grade its own work; the human decides."
  • There is no sub-agent tool at all. Never fabricate a dispatch: run the plan inline, and perform the final review yourself against the package, while telling the user plainly that "a self-review by the author is weaker than a fresh reviewer."
  • A spike. Explicitly permitted, explicitly outside the process: no tests or minimal ones, not bulletproof, skipping plan and review — and keeping it is a new request that re-enters the design gate.
  • A session went wrong. diagnosing-superpowers reads the session transcripts from disk, dispatches one analyst per dimension (plan adherence, repeated work, stumbles, cost and time, request conflicts, skill timeline, quality evidence), and reports findings that each cite path:line. "No citation, no finding." It is explicitly forbidden from proposing fixes.16

6.3 The trade-offs, stated plainly

DimensionSubagent-drivenInline (native)
Fresh context per taskYes — no context pollutionNo — one context does every task
Review gateSpec and quality review per taskOne whole-branch review at the end
CostA fresh context per task and per reviewOne context plus one final reviewer
Best forLong plans; every task worth a gateFully specified plans; a mid-tier session model
Main riskExpense; coordination overheadLate tasks run on a compacted context

Three further trade-offs are worth naming. Rigidity: the user can stall the whole run for one batch of questions, and the fix is escalation (the four stops) rather than elasticity — fast, but a badly chosen ruling costs visible rework. Model dependence: every rule is a markdown instruction, so compliance is a property of the model's training and its interpretation, not an enforced gate; the entire red-flags apparatus exists because instructions can be rationalized around. The maintainers took this seriously enough to build diagnosing-superpowers and a separate eval harness, superpowers-evals, for testing whether skills actually change behaviour.116

7 · Common misconceptions

  • "Superpowers is an AI model or an agent framework." It is a plugin: markdown procedures, a bootstrap hook, and a few shell scripts. It runs on top of Claude Code, Codex, Cursor, Gemini CLI, OpenCode, Kimi, Pi, Hermes, Muse, and others, and the repo maintains a separate manifest for each.
  • "It makes the agent write better code in one pass." Its main effect is on when code gets written and what must exist first: no code until an approved design, no production code without a test seen failing, no "done" without a fresh command output, no integration without your choice from a menu. The README's own framing is a methodology, not a generator.
  • "The plan contains the whole program." A plan that is longer than the code it describes has written the code instead, which the skill's own self-review flags. The plan is "the set of decisions the implementer cannot make alone": files, signatures, interfaces, exact spec values, and the tests.
  • "Sub-agents remember the conversation." They never inherit it. Everything a worker knows is in its dispatch prompt and the brief it reads. That is why the dispatch includes the report path and the interfaces from earlier tasks, and why the report is a file the fix rounds can append to.
  • "More agents mean more rigor." The skills repeatedly forbid redundant agents — workers must not spawn reviewers, reviewers must not spawn second reviewers, and a plan may not run two implementation workers at once. Extra agents a worker spawns "duplicate one of them at full cost, and its verdict counts for nothing."
  • "Approval of the idea means approval of the design." "Approval covers what you showed them. A design doc you haven't written isn't approved." The gate is on the document, not the vibe.
