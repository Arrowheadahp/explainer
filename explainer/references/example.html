How the internet delivers a web page

From one line in your browser to servers on the other side of the planet — and back — in under a second.

You type an address into your browser. A second later, a web page appears. Underneath that second sits a chain of machinery that took decades to build: a name-finding system, a reliable delivery system layered on top of an unreliable one, an encrypted conversation, and finally the actual page transfer. This page traces that chain end to end, names every artifact each phase leaves behind, and shows where the load genuinely has to stop and ask a human — which is once.1

1 · Prerequisites

Three ideas, briefly, before we start.

  • Packets. Everything sent over the internet is chopped into small chunks — packets — each carrying a destination address and its chunk of data. Packets are routed one by one, like letters through a postal system that reads addresses on envelopes.1
  • IP addresses and DNS. Every connected machine has a numeric address (like 142.250.190.4). Humans use names like example.org; the Domain Name System (DNS) is the directory that translates one to the other.3
  • Client and server. Your browser is the client: it asks. The machine holding the web page is the server: it answers. Everything below is a choreography between exactly these two roles.

2 · Big picture

Four phases, in order. First the browser converts the name (example.org) into an IP address. Then it establishes a reliable connection to that address. Then — usually — it upgrades that connection to an encrypted one. Only then does it ask for the page and receive it.

Figure 1 adds three things a phase list leaves out. It marks the artifacts — the cache entry, the open socket, the session keys, the rendered page — that each phase leaves behind and the next phase consumes. It marks the decisions as diamonds, because a cache hit really does skip work and a failed certificate really does end the load. And it marks the single point where you are consulted, in the accent colour: a certificate warning. Everything else in this page happens without asking.

3 · The mechanism, step by step

3.1 Finding the server: DNS

Your browser checks a chain of caches — its own, the operating system's, your router's, your ISP's recursive resolver. If nobody has the answer cached, the recursive resolver walks the DNS hierarchy: it asks a root name server which server is responsible for .org, then asks the .org (top-level domain) server which server knows example.org, then asks that authoritative server for the final IP address.3 The answer comes back with a time-to-live — how many seconds it may be cached. That cache entry is the phase's artifact: the next load of the same name never touches the hierarchy.

3.2 Building a reliable channel: TCP

The internet's delivery layer (IP) is best-effort: packets can be lost, duplicated, or reordered. TCP repairs this with a three-way handshake and sequence numbers:

Each byte is numbered. The sender retransmits whatever the receiver does not acknowledge; the receiver reassembles the bytes in order before handing them to the browser. This is why a download completes correctly even though no single network hop guaranteed anything.2 The handshake's artifact is the socket itself — a pair of agreed sequence numbers that both ends will honour for the rest of the connection.

3.3 Preventing eavesdropping: TLS

Before any page content moves, the browser and server run the TLS handshake. They agree on algorithms, the server proves its identity with a certificate signed by a public key your browser already trusts, and they derive shared session keys using key exchange (in TLS 1.3, an ephemeral Diffie–Hellman exchange). Everything after this is encrypted and authenticated.4

The certificate check is the only point in the whole procedure where the machine deliberately stops and consults a person, and only when something is wrong. Every other failure below is invisible: TCP retries, DNS re-asks, HTTP reconnects.

3.4 Asking for the page: HTTP

Over the encrypted connection the browser issues an HTTP request — GET / for the page's HTML. The server answers with a status code and the document. The browser parses the HTML, discovers further resources (CSS, JavaScript, images), and — thanks to keep-alive — reuses the same TCP/TLS connection to request many of them, or opens parallel connections to fetch several at once.5

4 · Worked example: counting the latency

Where does the "under a second" go? Say your browser to the server is 50 milliseconds away one way (RTT = 100 ms round-trip), the page is 200 KB, and the link carries 10 Mbps.6

  • TLS latency: 2 round trips (TLS 1.3, resumption aside) = 200 ms
  • Transmission time of the page:

\[ t_{\text{tx}} = \frac{\text{size}}{\text{bandwidth}} = \frac{200 \times 2^{10} \times 8\ \text{bits}}{10 \times 10^6\ \text{bps}} \approx 0.164\ \text{s} \]

PhaseRound tripsTime
DNS lookup (nothing cached)≈ 3300 ms
TCP handshake1100 ms

Transmit 200 KB—164 ms
Total≈ 0.86 s

Two things fall out of the table. First, latency — not bandwidth — dominates small, interactive pages, which is why DNS and handshake round trips matter so much. Second, DNS is amortized: a cached lookup turns 300 ms into nearly nothing on a second visit. Section 5 makes that concrete, by asking which of these costs an artifact actually removes.

5 · Artifact inventory

Each phase leaves something behind that the next phase consumes, and that a later visit can reuse. This is the part a phase list hides: the expensive work is the creation of the artifacts, and the fast path is their reuse.

[session keys]

[rendered page]

Two of the four survive the run — the DNS cache entry and whatever the HTTP cache keeps — and they are the only reason a second visit is faster. The socket and the session keys are deliberately thrown away, because a connection that outlives its keys is exactly what forward secrecy is meant to prevent.4

6 · Deeper layers

6.1 The bandwidth–delay product

How much data can be "in flight" before the sender must stop and wait?

\[ \text{BDP} = \text{bandwidth} \times \text{RTT} = 10\ \text{Mbps} \times 0.1\ \text{s} = 1\ \text{Mbit} = 125\ \text{KB} \]

This is the pipe's capacity. If the connection's congestion window is smaller than this, the link is under-used; early in a connection TCP's congestion window start typically under-fills the pipe, which is why the first response byte is slow to stream.2

6.2 Why layers

DNS, TCP, TLS, and HTTP each solve one problem and ignore the others. DNS knows nothing about encryption; TCP knows nothing about web pages. This layering is the internet's central design idea — it lets each protocol be invented, replaced, and improved independently. (TLS 1.3 shaved TLS handshakes from two round trips to one largely without touching anything below it.4)

The artifact list in §5 is the layering seen from the other side. Each layer produces a by-product in its own vocabulary — a name record, a socket, a key set — and none of them means anything to the layer above.

7 · Common misconceptions

  • "The internet is a cloud." It is a mesh of physical cables, routers, and data centers — famously including submarine cables whose failures make headline news.
  • "HTTPS is 'the secure button'." HTTPS is TLS layered over HTTP: it encrypts and authenticates one connection. It does not make the server itself honest, and metadata (who you talked to, when) still leaks.
  • "One query = one server." A single page can touch DNS resolvers, several authoritative servers, CDN edges, and origin servers — dozens of machines.
  • "The page loads the same way every time." From a warm DNS cache and a kept-alive socket, the 860 ms in §4 collapses to roughly the transmission time — which is why the artifacts, not the phases, are the thing to optimize.
